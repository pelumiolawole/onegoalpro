fix: validate task_type in code before persist, closing a DB-crash gap

_validate_task now checks task_type first - cheapest check, and the one
that previously reached the database with zero validation. Confirmed in
production July 21 (Sentry issue #40): the AI returned
task_type: "reflection" (a domain name, not a valid task type) and the
value went straight into an INSERT, crashing with asyncpg's
InvalidTextRepresentationError against the task_type enum. The user
still got a task that day via the backlog recovery path, but the crash
itself was avoidable.

Adds VALID_TASK_TYPES (becoming, identity_anchor, micro_action,
challenge - matching both the prompt and the actual DB enum) and a new
"invalid_task_type" reason code with its own retry guidance: same task
idea, fix the one bad field, and an explicit note that task_type and
domain are separate fields. Same pattern as every other check in this
file - reject, name the problem, one retry with concrete guidance,
fallback only if that also fails.
